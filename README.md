# Expense Tracker

An offline Android app for recording income and expenses, with an optional
per-month backup to your own Google Drive.

Everything you enter lives in a SQLite database on your phone. Nothing is
uploaded anywhere unless you tap the export button, and the only Google
permission the app requests is `drive.file` — it can see the backup files it
created itself, and nothing else in your Drive. [PRIVACY.md](PRIVACY.md) spells
this out in full.

## Download

Grab the latest APK from the
[Releases page](https://github.com/Zierch/expense_tracker/releases) and open it
on your phone. Android will warn you that the app comes from an unknown source,
which is expected: it is not distributed through Google Play. You will need to
allow installation from your browser or file manager when prompted.

> **Google Drive backup needs you to be on the test-user list.**
> While this app is in development, its Google sign-in runs on an OAuth consent
> screen that is still in *Testing*, and Google only lets approved accounts
> through. Everybody can use the app and all of its offline features; only the
> Drive export is limited. To be added, open an issue with the Google address
> you want to use. The list is capped at 100 accounts by Google.

> **Updates.** Newer releases are offered in the app itself: when a new version
> is published on the Releases page of this repository, the app offers to
> download and install it — it contacts GitHub's public release API, verifies
> the APK against the checksum the release publishes, then opens Android's
> installer. Nothing else leaves the device; the update check and the backup
> are the only two networked features, both detailed in `PRIVACY.md`.

Requires Android 7.0 or newer (minSdk 24).

## Features

- Add, edit and delete income and expense transactions
- Categories and subcategories, kept separate for income and expense
- Monthly summary: total income, total expense, balance
- Hide or show the balance with the eye on that card; the choice is remembered
  for the next launch
- Weekly summary showing one total per week, with daily and weekly breakdowns
  kept as separate views
- Statistics split into an Expense tab and an Income tab, with a category-by-
  category breakdown and a pie chart for expenses
- Amount entry with quick-append buttons for `0` / `00` / `000`
- Indonesian rupiah (IDR) formatting
- Optional per-month JSON export to a `Expense Tracker` folder in your own
  Google Drive; re-exporting a month replaces its file instead of duplicating it
- PDF report for any date range, with totals, a breakdown per category and every
  transaction; shared straight to Files or a chat from Android's share sheet, and
  no Google account needed
- Follows your system light or dark theme, or force light/dark from the theme picker on the dashboard
- Checks GitHub for a newer release on open (and on demand from Backup), downloads and installs it in place
- Pull the dashboard down to re-run the queries behind the month on screen
- The month on the dashboard is named above the card and chosen by tapping that
  name; the picker offers months only, from January 2020 up to the current one
- Works entirely offline

## Tech stack

| Concern | Choice |
|---|---|
| Framework | Flutter (Android only) |
| Database | Drift over SQLite |
| State | Riverpod |
| Navigation | GoRouter |
| Charts | fl_chart |
| Value types | Freezed |
| Formatting | intl |
| Sign-in and upload | `google_sign_in` plus the Drive v3 REST API |
| PDF report | `pdf` to draw it, `printing` to hand it to the share sheet |

The app is deliberately Android-only. Drift needs a native SQLite library, so
there is no web target and `flutter run -d chrome` will not work.

## Building from source

You need the Flutter SDK and an Android SDK. Then:

```bash
flutter pub get
flutter run
```

Debug builds work without any further setup. Google Drive backup will not work
until you register your own OAuth client — see below.

### Generated code

The Drift database classes are generated by `build_runner` and are committed to
the repository, so you do not need to run code generation to build the app. If
you change a table definition, regenerate them with:

```bash
dart run build_runner build --delete-conflicting-outputs
```

CI regenerates them on every push and fails if the result differs from what is
committed, so a generated file left stale does not stay unnoticed.

## Building a release APK

Release builds are deliberately **not** signed with the debug keystore, and the
build fails rather than quietly producing an artifact that cannot be updated
later. This matters more than it sounds: Android refuses to install an update
whose signing certificate differs from the installed one, and a debug keystore
is generated per machine and easily lost. Shipping a debug-signed APK means that
the first time you rebuild it from anywhere else, every user has to uninstall —
which deletes their database.

1. Create a keystore. Store it and its passwords somewhere you will not lose
   them; losing this file means you can never update an app you have already
   shipped.

   ```bash
   keytool -genkeypair -v \
     -keystore android/app/release-keystore.jks \
     -keyalg RSA -keysize 2048 -validity 10000 \
     -alias expense-tracker
   ```

2. Copy the template and fill in your credentials:

   ```bash
   cp android/key.properties.example android/key.properties
   ```

   `storeFile` is resolved relative to `android/app/`, so the default value
   `release-keystore.jks` matches the keystore created above.

3. Build:

   ```bash
   flutter build apk --release
   ```

4. Confirm the artifact is signed with *your* key and not the debug one:

   ```bash
   apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
   ```

   The `certificate DN` must show the name you entered in step 1. If it says
   `Android Debug`, something is wrong — do not hand that APK to anybody.

`android/key.properties` and any `*.jks` / `*.keystore` file are git-ignored.
Never commit either one.

A plain `flutter build apk --release` produces a single universal APK that runs
on every device, which is the simplest thing to share. If download size matters
more, `flutter build apk --split-per-abi` writes one smaller APK per CPU
architecture, and you would share the right one for each phone.

### Publishing a release

[`.github/workflows/release.yml`](.github/workflows/release.yml) builds, signs and
publishes the APK when a version tag is pushed, so the published artifact is
always the tagged commit rather than whatever was on a laptop.

1. Write the notes to `docs/releases/v<version>.md`. If the first line is a
   `# heading`, it becomes the release title; the build details (versionCode,
   SHA-256, commit) are appended by the workflow, because they do not exist until
   the APK does.
2. Bump `version:` in `pubspec.yaml` — the last number by default, see
   [AGENTS.md](AGENTS.md) — and commit it as `chore: release <version>`.
3. Push that commit and wait for `CI` to be green.
4. Tag it and push the tag:

   ```bash
   git tag v1.4.2
   git push origin v1.4.2
   ```

The `Release` run waits for approval from the reviewers on the `release`
environment, then runs the suite, builds, checks the signing certificate, and
publishes the APK as `expense-tracker-<version>.apk`.

Releases up to v1.4.3 carried a second copy under `app-release.apk`, because a
build older than v1.3.1 looks for that name and nothing else, and its updater is
already on phones. Publishing the new name alone would have left exactly those
phones unable to update; the duplicate was dropped once nobody was still on one.
`apkFileNameFor()` still accepts the old name, so a release that carries only it
— an old one, or a hand-made upload — remains updatable.

If the run fails after the tag is published, fix forward with the next patch
rather than moving or deleting the tag: the updater has already read it.

**One-time setup.** The keystore must never be in the repository, so it travels
as an environment secret:

```bash
base64 -w0 android/app/release-keystore.jks | gh secret set ANDROID_KEYSTORE_BASE64 --env release
gh secret set ANDROID_STORE_PASSWORD --env release   # prompts for the value
gh secret set ANDROID_KEY_ALIAS --env release
gh secret set ANDROID_KEY_PASSWORD --env release
```

`ANDROID_KEYSTORE_BASE64` is the keystore file itself; the other three hold the
values from `android/key.properties`. The `release` environment should name a
required reviewer, so a run nobody approved cannot read the key. Anyone who can
push a tag to this repository can reach those secrets — which is why cutting a
release is a maintainer action. Building locally with
`flutter build apk --release` still works and remains the fallback if CI cannot
run; attach `expense-tracker-<version>.apk` by hand in that case.

## Verifying a download

Nobody has to take the APK on faith: the release notes carry the SHA-256 of that
release's build, and its signing certificate is public. Before installing:

```bash
sha256sum expense-tracker-1.4.0.apk          # Windows: certutil -hashfile expense-tracker-1.4.0.apk SHA256
apksigner verify --print-certs expense-tracker-1.4.0.apk
```

Substitute the file you actually downloaded: every release from v1.3.1 on is
`expense-tracker-<version>.apk`, and older ones are `app-release.apk`.

`apksigner` ships with the Android SDK's `build-tools` and needs a JDK on the
PATH. It prints the certificate's SHA-1 lowercase and without separators, so the
value it reports has to be `b2f50e9c44f5724b9e17b57bd7b6a3e624f42cae` — the same
fingerprint that [docs/google-cloud-setup.md](docs/google-cloud-setup.md) shows
colon-separated. `certutil` prints the digest too, but some Windows builds add
spaces or change letter case, so compare digit by digit rather than pasting the
whole line. The SHA-256 has to equal the one in that release's notes.
Anything else is not this project's APK: delete it rather than installing it,
because it would be asking for the same Google Drive access under a name you
cannot check.

Verifying a file is one half; knowing where it came from is the other. A
forwarded copy of the real APK would verify fine, but nothing tells you that what
a chat app handed you is that copy — and a rebuild by anybody else will never
match this fingerprint at all. Install from the
[Releases page](https://github.com/Zierch/expense_tracker/releases) only.

## Using your own Google OAuth client

The APK on the Releases page is signed with the maintainer's key, so it works
out of the box. **A build you compile yourself will not.** That is intentional:
Google binds an OAuth client to exactly one package name plus one signing
certificate, so a client registered for someone else's key cannot authorise your
build.

A click-by-click walkthrough of the Console, with the exact package name,
fingerprints and the file to paste the client ID into, is in
[docs/google-cloud-setup.md](docs/google-cloud-setup.md). The short version:

1. In the [Google Cloud Console](https://console.cloud.google.com/), create a
   project and enable the **Google Drive API** for it.
2. Configure the OAuth consent screen. Choose **External**, and add your own
   Google address under **Test users**. Because this app requests only the
   non-sensitive `drive.file` scope, Google does not require an app verification
   review for personal use.
3. Create an OAuth client ID of type **Android**, with:
   - package name `com.zierch.expense_tracker`
   - the SHA-1 fingerprint of the certificate you build with:

     ```bash
     keytool -list -v -keystore android/app/release-keystore.jks -alias expense-tracker
     ```

     For a debug build, the fingerprint belongs to
     `~/.android/debug.keystore`, whose password is `android` and whose alias is
     `androiddebugkey`.
4. Create a second OAuth client ID of type **Web application**. The Android
   Sign-In SDK needs this one at runtime; it is what lets the app obtain the
   Drive scope.
5. Put the **Web application** client ID into
   `lib/data/services/google_config.dart`:

   ```dart
   static const String serverClientId = '<your-id>.apps.googleusercontent.com';
   ```

A client ID is not a secret: it identifies the application, not the user, and
committing it is normal for a public client. The **client secret** shown next to
it in the Console must never be added to this project — if Google ever asks this
app for a secret, something has been configured wrongly.

If you later publish through Google Play, Play App Signing re-signs your upload,
which gives the shipped app a *second* SHA-1. That fingerprint has to be
registered as well, or sign-in will fail only in the Play-distributed build.

## Tests

```bash
flutter test
```

The suite covers the monthly export format, month navigation (including the
year-boundary arithmetic), the month boundaries themselves — the in-memory predicate
and the SQL range, run against a real in-memory database — the dashboard's month
picker (which months it offers, and that a choice comes back as a month anchor), the
transaction row widget, the dashboard's pull-to-refresh, the balance's hide/show
toggle, and the release-config invariants that keep signing, backup rules and the
OAuth identity from silently regressing.

The database-backed tests need a SQLite library for the *host* to load, which is a
different build from the one the app ships: Windows uses the `winsqlite3.dll` that
ships with the OS, Linux needs `libsqlite3` installed. Where none can be loaded those
tests are reported as skipped rather than failed.

## Continuous integration

Every push to any branch runs [`.github/workflows/ci.yml`](.github/workflows/ci.yml)
on GitHub Actions: `flutter analyze`, `flutter test`, and a check that the
committed generated code still matches its sources. The trigger is a push rather
than a pull request on purpose: a `pull_request` run checks out the merge branch,
which mixes in whatever landed on `main` after your branch was cut, and the first
thing worth knowing is whether *your* branch is green. `main` is covered by the
same trigger, so a merge is verified again once it lands.

The generated-code check regenerates the Drift, Freezed and Riverpod output and
then fails if the working tree changed, which is what catches a table or a
provider edited without regenerating. CI also installs `libsqlite3-dev`, so the
database-backed tests run there instead of being reported as skipped.

That install is the one step that talks to a package mirror rather than GitHub,
and it has hung once: on 22 October 2026 a `Release` run sat on it for 21 minutes
until it was cancelled, against 5 seconds for the same step an hour earlier. The
symptom is a run parked on **Install host SQLite** while every later step stays
queued; nothing in the build is wrong and a re-run has picked a working mirror
every time. Two things to do about it, in order:

1. Cancel and re-run. If it hangs twice in a row, cut the release locally
   instead — see [Publishing a release](#publishing-a-release) — rather than
   waiting on a mirror.
2. When it next bites, bound it rather than only working around it: give the step
   `timeout-minutes: 5` and run `apt-get update` with
   `-o Acquire::http::Timeout=20 -o Acquire::Retries=3`, plus a
   `ldconfig -p | grep -q libsqlite3.so && exit 0` short-circuit so a runner that
   already has the library skips the network entirely.

Analysis is deliberately not fatal on the `info` category: those findings are
printed for whoever wants to act on them, but the run fails only on errors and
warnings. The generated `*.g.dart` and `*.freezed.dart` files are excluded from
analysis entirely, because their contents follow whichever version of the
generator produced them rather than this project's lint configuration. The suite
runs before the lint step, so a style finding cannot hide whether the tests pass.

Two things it does not do. It does not build the release APK — that needs a
signing keystore, which must never leave the maintainer's machine (see
[Building a release APK](#building-a-release-apk)). And it does not exercise a
real Android runtime: there is no emulator job, because `flutter test` runs on
the host Dart VM, and an emulator would add minutes and flakiness for little.

## Troubleshooting

**`Could not close incremental caches ... class-fq-name-to-source.tab`**

Kotlin's incremental compilation fails to close its memory-mapped cache files on
this toolchain (Kotlin 2.4.0 with Gradle 9.3.1 on Windows), which aborts the
build of `:google_sign_in_android`. `android/gradle.properties` therefore sets
`kotlin.incremental=false`. It costs a little build time and changes nothing
about the output. Delete the line if your machine does not have the problem.

**`clientConfigurationError` when signing in**

Google rejected the app's identity. Check that the package name, the certificate
SHA-1 and the client type all match what you registered, and that the Android
client's SHA-1 is from the keystore you actually built with. Console changes can
take a few minutes to propagate.

**The app installs but the launcher icon did not change**

On MIUI and some other Android skins the launcher caches icons. Remove the app
from the recents list and launch it again, or reboot. Clearing the system
launcher's cache also works.

**`INSTALL_FAILED_USER_RESTRICTED` during `flutter run`**

Your phone is blocking the install. Accept the prompt on the device; on MIUI you
may also need to enable *Install via USB* in developer options.
